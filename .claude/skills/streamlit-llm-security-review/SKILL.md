# Streamlit × LLM アプリのセキュリティレビュー

## このスキルの狙い

汎用の脆弱性スキャンをこの手のアプリに当てても、あまり当たらない。SQL インジェクションも
CSRF トークンの検証漏れも、そもそも存在しないことが多いからだ。代わりに事故が起きるのは、
ほぼ次の 3 本のデータフローのどこかである。

1. **秘密情報のフロー** — API キーはどこから入り、どこへ出るか。
   出口は画面・エラーメッセージ・ログ・リポジトリの 4 つ。
2. **信頼できないテキストのフロー** — 誰かが書いた文章（貼り付けたメール、取得した Web ページ、
   アップロードされたファイル）が、どこでプロンプトの一部になるか。
3. **モデル出力のフロー** — 生成されたテキストが、どこで「ただの文字」以上のもの
   （HTML、実行されるコード、ファイルパス、次の API 呼び出しの引数）になるか。

この 3 本を最後まで追い切ることを、レビューの背骨にする。カテゴリを機械的に舐めるより
当たり判定が高く、報告が具体的になる。

## 手順

### 1. 前提を確定する

同じコードでも、置かれ方で深刻度が二段変わる。ローカルの自分専用なら「API キーが画面に出る」は
軽微だが、社内 LAN に公開しているなら重大だ。だから最初に確認する。

- どこで動かすか（ローカルのみ / 社内 LAN / Streamlit Community Cloud / 自前サーバー）
- 誰が使うか（自分だけ / チーム / 不特定）
- API キーは誰のものか（個人の従量課金 / 会社の共有キー）

リポジトリから読み取れることも多い（README、`.streamlit/config.toml`、Dockerfile、
デプロイ設定）。まず自分で調べ、それでも分からず、かつ深刻度の判断が割れる場合にだけ聞く。
判断できないまま止まるより、**「ローカル前提。公開するなら別途この項目が効く」と前提を明記して
進めるほうがよい**。前提はレポート冒頭に必ず書く。

### 2. 地図を作る

同梱のスクリプトが、上の 3 本のフローに関わる箇所を機械的に洗い出す。毎回同じ grep を
書き直す必要はない。

```bash
python <skill-path>/scripts/recon.py <project-root>
```

出るのは「候補地点」であって「脆弱性」ではない。ここを起点に、次のステップで人間の目で読む。
スクリプトが何も出さないカテゴリも、コードを読んで裏を取る（正規表現で拾えない書き方は普通にある）。

### 3. カテゴリごとに読む

`references/checklist.md` に、カテゴリ別の「なぜ危ないか / 見つけ方 / 誤検知しやすい点 / 直し方」を
まとめてある。**レビュー中に必ず読むこと。** 特に Streamlit 固有の罠（キャッシュ越しの
セッション間漏れ、認証機構が存在しないこと、既定で全インターフェイスに待ち受けること）は
一般的なセキュリティ知識からは出てこない。

カテゴリは 8 つ：秘密情報 / プロンプトインジェクション / モデル出力の描画 / モデル出力の副作用 /
入力の受け口 / 保存・ログ・履歴 / 公開と運用 / 依存関係。

### 4. 所見を裏取りする

ここが報告の質を決める。**候補を見つけたら、必ずその行と周辺を実際に読んでから書く。**

各所見について答えを持っていること：

- **どう悪用されるか** — 攻撃者は誰で、何を入力し、何を得るか。一本の筋として書けないなら、
  それはまだ所見になっていない。
- **前提は成立するか** — 「公開されていれば」「ユーザーが他人の文章を貼れば」。
  前提が成り立たない環境なら、深刻度を落とすか、前提付きで書く。
- **すでに緩和されていないか** — 例えば `st.markdown()` は既定で生 HTML をエスケープするので、
  `unsafe_allow_html=True` が無ければ XSS にはならない。フレームワークが既に守っている
  ことを「脆弱性」として報告すると、レポート全体の信用が落ちる。

裏が取れなかったものは捨てるか、「要確認」として別枠に置く。**確認済みと推測を混ぜない。**

### 5. レポートを書く

プロジェクトルートに `SECURITY_REVIEW.md` を作る。既にあれば中身を確認し、
上書きしてよいか判断する（前回分を残すなら `SECURITY_REVIEW_YYYYMMDD.md`）。

言語はプロジェクトの既定に合わせる。日本語のコードベースなら日本語で書く。

レポートを書いたら、会話には**要約だけ**を返す。深刻度ごとの件数、最も効く 1〜3 件、
ファイルのパス。全文を会話に貼り直さない（読む場所が二つあると、どちらも読まれない）。

## レポートの形

```markdown
# セキュリティレビュー: <アプリ名>

**対象**: <パス>（<コミット or 日付>）
**前提**: <どこで誰が動かす想定か。API キーの持ち主。>
**総評**: <2〜3 文。今すぐ直すべきものがあるか、公開してよい状態か。>

| # | 深刻度 | 概要 | 該当箇所 |
|---|--------|------|----------|
| 1 | 高 | エラー文の生テキストをそのまま画面に出しており、例外に API キーが含まれると露出する | gemini_client.py:150 |

---

## 1. <所見のタイトル>

**深刻度**: 高
**該当**: `path/to/file.py:120-135`

**何が起きるか**
<攻撃の筋を一本で。誰が、何を入力し、何を得るか。>

```python
# 該当コード（数行だけ引用する）
```

**なぜそうなるか**
<コードのどの性質が原因か。>

**直し方**
```python
# 修正案。動く形で示す。
```

**残る懸念** *(あれば)*
<この修正で消えないもの。>

---

## 確認したが問題なかった項目

- **モデル出力の HTML 描画**: `unsafe_allow_html` の使用箇所なし。`st.markdown()` は
  既定で生 HTML をエスケープするため、XSS の経路は無い。
- ...

## 要確認（コードからは判断できなかった）

- <前提が分からず深刻度を決められなかったもの。何を確認すれば決まるかを書く。>
```

「問題なかった項目」の節は省かない。**何を見なかったかが分からないレポートは、
次に読む人がゼロから見直す羽目になる。** 一行ずつでよい。

## 深刻度の基準

| 深刻度 | 目安 |
|--------|------|
| 重大 | 前提なしに、秘密情報の流出・任意コード実行・第三者による金銭被害が起きる |
| 高 | 現実的な前提（公開している、他人の文章を貼る）が揃えば上記が起きる |
| 中 | 被害が限定的、または攻撃に手間・偶然が要る |
| 低 | 実害は薄いが、設計として直しておくべき |
| 情報 | 現状は問題ないが、公開・多人数利用に移すときに効く |

**深刻度は前提とセットで決める。** ローカル専用アプリの「認証がない」は情報レベルだが、
社内公開なら高になる。同じコードでも判断が変わるのが正しい。

## やらないこと

- **動く攻撃コードを書かない。** 何が起きるかは説明するが、そのまま使える exploit は書かない。
  レビューの目的は直すことであって、攻撃の道具を残すことではない。
- **件数を稼がない。** 「入力値検証が不十分かもしれません」のような、どこを直せばいいか
  分からない指摘は、無いほうがましだ。読み手の時間を奪い、本当に重要な 1 件を埋めてしまう。
- **勝手に直さない。** 指摘と修正案までがこのスキルの仕事。コードの変更を頼まれたら、
  レポートを出したあとで、どれを直すか合意してから着手する。
- **一般論を並べない。** 「HTTPS を使いましょう」の類は、そのアプリの具体的な箇所を
  指せないなら書かない。
